先看一家小饭馆

一桌客人点了三道菜。

后厨不会"把三道菜一起做完"。它的做法是：做第一道，端出去，回头问一句"还有菜吗"；有，做第二道；再问；做第三道；再问；没有了，收工。

循环条件就一句话：还有菜吗。

但做一道菜本身也不是一件事。红烧肉要焯水、上色、焖。每做完一步都要看一眼：这一步够了吗？ 不够就再焖一会儿，够了就进下一步。

这里有件事值得停一下：

  • 外层问的是"还有没有新的活"
  • 内层问的是"这单还欠不欠工序"

两句话长得像，问的却是两件事。一个是"还有下一位客人吗"，一个是"这位客人的菜齐了吗"。混在一起想，后面全乱。

三层循环问的是同一句话，只是粒度一层比一层细：还有活吗。

换成 CI 流水线

同一个结构，换身衣服。

一条流水线跑完一个 commit，里面可能有 build、test、deploy 若干个 job。跑完 build，流水线回头问"后面还有 job 吗"；有就继续，没有就结束这一轮。

而单个 job 内部如果拉依赖失败了，会重试三次。这是第三层，问的是"这次尝试成功了吗"。

三层，问的都是一件事：还欠不欠。只是粒度一层比一层细。

02

两条队列

代码：code/step3.mjs code/step3b-scenarios.mjs code/step3c-steer-admission.mjs
对照：packages/core/agent-loop/src/inbox.ts、agent.ts:163-173、packages/api/session-controller/src/commands.ts:364-365,477-478

一个我信了很久的误解

"消息队列嘛，先进先出。"

第一次在 DSH 里看到 next-turn 和 next-step 两个队列时，我以为是把同一个东西拆成了两份。

这个判断是错的。它们装的是两种完全不同的活，而这个区分决定了三件看起来很怪的事：为什么用户连发三条消息不会一次全喂给模型、为什么"插话"和"发消息"是两个入口、为什么空闲的时候不能插话。

队列的数量不是设计出来的，是被消费规则逼出来的。

一条队列只能有一个消费规则

场景：用户发了一条"这个项目用什么测试框架？"，模型说"我要 grep 一下"，于是有了工具结果。

这个工具结果不是用户发的新消息，但它同样是要处理的东西。塞进同一条队列会出什么问题？

问题在于这两类东西的消费规则恰好相反：

用户的新消息，一次只能取一条。三条一起问模型，模型就分不清该回哪一条。

当前这一轮的中间产物，一次要全取。工具结果、运行时上下文，本来就是这一步要用的配料，留到下一轮就过期了。

规则相反，就不能共用一条队列。

两条规则

code/step3.mjs 里的 claim 就是这两条规则：

看 claim 后面的参数：第一次是 next-turn，第二次变成了 next-step。

这不是谁传进去的，是循环自己换的——轮次的第一个步骤在轮次边界取输入，之后只取当前这一轮的。

落点决定一切

followup、steer、inject 三个入口，代码上只差一个参数：

入口 落到哪 唤醒吗
followup next-turn 唤醒
steer next-step 唤醒
inject next-step 不唤醒

落到 next-turn 就开新的一轮；落到 next-step 就只影响当前这一轮的下一个步骤。

code/step3b-scenarios.mjs 把两种落点摆在一起：

用户插话：

同样是用户的一次动作，落点不同，结果差一整轮。

为什么空闲时不能插话

code/step3c-steer-admission.mjs 补上最后一块：

steer 承诺的是"插进当前这一步"。如果没有正在跑的轮次，就没有"当前这一步"可插——承诺兑现不了，所以直接拒绝。

inject 不一样。它不承诺插进哪一轮，只是把东西放进队列等人来取。所以它不校验，也不唤醒。

输出里还有一段，正好验证了上一节的规则：

注入的那条躺在 next-step 里没人叫醒它。等有人 followup 时，轮次边界的 claim 顺手把它一起取走了——next-step 全取，next-turn 一条。

它不在内存里

队列是持久的。

每次增删都会写一条 agent/inbox/spliced 事件，队列状态从这些事件投影出来。所以进程重启之后，还没处理的排队消息还在。

这也是 claim 要接受一个 turn 参数的原因：重放的时候，得能还原"这条消息属于哪一轮"。

下次再看到两个队列、三个入口，你不会再问"为什么要这么多"，而是先问一句：它们的消费规则差在哪。

03

一个字的三条路

代码：code/step4-stream.mjs
对照：packages/core/agent-loop/src/assistant-stream.ts:60-71、agent.ts:436-528、packages/llm/llm/src/types.ts:452

我以为流式只是为了"快"

看到 for await (const chunk of stream) 的时候，我的第一反应是：这是为了让用户早点看到字。SSE 嘛，打字机效果。

这个理解只对了三分之一。

同一个 chunk，在这套系统里有三个消费者，而它们的要求互相冲突。只按"让用户早点看到"来设计，另外两个会出问题。

同一个字，要同时满足三个互相冲突的要求。

三个人，三种要求

界面要的是立刻。晚一百毫秒，用户就觉得卡。它不关心完整不完整，来一片显示一片。

会话日志要的是完整准确。少一片，回放的时候就缺一块。它不着急，可以等流结束再落盘。

模型历史要的是干净。下一轮请求里要的是"模型上次回答了什么"，不是七个碎片。

三份需求，一个数据源。

Attempt.push() 里那三行，就是分别写给这三个人的：

前面那一串 ⚡ 是一路闪过去给界面看的。底下两行才是留下来的东西：一句完整的话，和一份 7 片的原始录像。

为什么录像不能省

既然已经折叠成完整消息了，为什么还要留那 7 片？日志不是越干净越好吗？

因为"完整消息"是加工过的。加工就会丢信息。

具体的例子：模型输出到一半被取消，或者流断在半路。这时候"完整消息"根本不存在——你不能拿一个不存在的加工结果去解释发生了什么。但你手里有录像，就能还原它当时到底吐了哪几个字。

真实系统里这份录像挂在 assistant/message 事件上（agent.ts:527 的 stream: live.stream）。它不是独立事件，是消息自己的附件。所以既不膨胀日志，也不丢证据。

惰性那个坑

第一次跑会看到一件怪事：

"发给模型"出现在 start 之后，看着像顺序错了。

其实没错。mockModelStream() 是个 async generator，调用它不会执行任何代码，直到第一次 next() 才开始跑。而代码是先发 start 帧，再开始消费流。

真实代码也是这个顺序（agent.ts:438-440）。所以这是忠实的，不是 bug。

生成和验证

这里有个值得记下的规律：生成一件东西，比验证一件东西容易得多。

写下 push() 存住每一片，是生成。但它对不对，不靠"我写得挺仔细"来保证，靠的是"把日志读出来重放一遍，看是不是和当初一样"。

那 7 片录像存在的意义，就是让"验证"这件事成为可能。

以后再看到任何流式输出，你的第一反应会是：这一小片，它同时给了谁。

04

重试不是新步骤

代码：code/step5-retry.mjs
对照：agent.ts:407（attempt 循环）、agent.ts:494-509（失败后问监听器）、packages/llm/llm/src/index.ts:1146（错误变 chunk）

我以为 request-error 是错误处理

源码里有个事件叫 agent/request-error。看到名字，我的第一反应是：这是出错之后的收尾逻辑。

不是。它是重试的入口。

这个误会不小，因为它会让人把"重试"和"新一轮"混在一起想。而这两件事在结构上是分开的——分开得很彻底。

重试复用一切，唯独重发。

第三层循环

code/step5-retry.mjs 在 step() 里面又嵌了一个 while：

跑出来是这样：

两次请求，但 step/start 只出现了一次。

这就是这一层的全部意义：attempt 循环转多少圈，都算同一个 step。

那行"组装"的位置

注意 request 是在 while 外面构造的。

把它挪进循环里也能跑，输出看不出差别。但语义就错了——那样每次重试都会重新组装一遍请求，而在真实系统里，重试是"把同一份请求再发一次"，不是"重新写一份请求"。

真实代码里 prepareRequest 和 agent/pre-step 都在 attempt 循环外面（agent.ts:407-408）。所以重试不会重跑 pre-step、不会重新组装提示词、也不会重复追加用户消息。

最后这点是可以验证的。跑完看日志：

发了两次请求，用户消息只记了一次。

失败是个 chunk，不是异常

上一章说过，同一个 chunk 有三个消费者。这里用上了这个设计的好处：失败也是流的一部分。

所以上层不用写两套错误处理——一套管"网络抛异常"，一套管"流里说失败了"。它只看 finish.kind。

真实代码在 adapter 边界做这个转换（llm/index.ts:1146），一行函数把任何异常变成一个终结 chunk。

重试几次，谁说了算

玩具里是一个回调。真实代码里是一个 waterfall（agent.ts:494-504），而且顺带把 retryPolicy 一起传进去。

这一点值得留意：重试策略是路由决定的，不是全局写死的。

换一个模型提供方，重试次数和退避算法可以完全不同。如果写成一个全局常量，换提供方就得改循环代码——而循环代码是不该知道这些的。

没人接管会怎样

code/step5-retry.mjs 的第二个场景就是这种情况：

抛出去，这一轮以 error 收尾。turn/end 的 reason 会把这件事记下来。

到这里三层循环就齐了：kick 管轮次，turn 管步骤，step 管重发。重试只影响最里面那一层，外面两层完全不知道发生过。

以后再看到 retry，你要问的不再是"重试几次"，而是"重试的时候，哪些东西是不重新算的"。

05

停下来之后

代码：code/step6-cancel.mjs
对照：agent.ts:175-181（cancel 实现）、:440-443（检查点）、:448-477（两种收尾）、:366-371（拷贝原因）

"取消不就是停止吗"

模型正在吐字，用户点了停止按钮。

我以为这件事的难点在"怎么停下来"——大概是给流发个信号，然后它就不吐了。

停下来确实不难。难的是停下来之后。

屏幕上已经有半句话了。日志里要不要记？如果不记，用户重新打开这个会话，会发现自己刚才明明看到了内容，现在却什么都没有。

取消的难点从来不是停下来，是停下来之后留下了什么痕迹。

两种停止，两种收尾

code/step6-cancel.mjs 跑了两个场景，差别只在一个时间点。

吐到一半才停：

一个字都没吐就停：

同样是取消，结果完全不同。

停止时机 记什么 进模型历史吗
已经吐了内容 assistant/message + interrupted: true 进
一个字都没吐 assistant/attempt 不进

为什么必须分开

已经吐了内容的情况：用户屏幕上看到了。日志里不记，重放的时候这半句话就消失了——用户会觉得消息丢了一截。而且下一轮请求里模型也不知道自己刚才说过什么，可能把同样的话再说一遍。

一个字都没吐的情况：往模型历史里塞一条空消息，纯属污染上下文。所以只留一条"仅日志"的事件，证明"这里尝试过、但没产出"。

真实代码里这是 agent.ts:448-477 的那两个分支。

这里有个让人安心的地方：这两个分支不是为取消专门写的。assistant/attempt 一直是那个"只进日志、不进模型历史"的事件——上一章里重试失败用的是它，这里取消用的还是它。新场景，旧机制。

取消什么时候生效

对应 agent.ts:440-443 的 signal.throwIfAborted()。

注意检查点在每一块之前。所以取消的粒度是"一块 chunk"，不是"立刻"。

如果模型正在长时间思考、一个字都还没吐，取消要等到下一块到达才生效。真实系统里这种"卡住不动"的情况由 adapter 的 idle 超时兜底——下一章会碰到它。

这个设计是有意的：取消是协作式的。每个可能耗时的环节自己检查信号，而不是从外面强行打断。因为强行打断会留下半死不活的状态——一半的写操作做完了，另一半没做。

一个不会注意到的细节

真实代码在写 turn/end 的取消原因时，会先拷贝一份（agent.ts:366-371）。

原因很具体：AbortSignal.reason 就是调用方传进来的那个对象。而 Node 的 fetch 会往上挂一个 stack 属性。如果不拷贝直接写进日志，调用栈就被写进会话文件了——体积变大，而且对用户毫无意义。

拷贝一份，既挡住了这个，又保持了结束事件可以安全追加。

这种细节不会出现在任何架构图里。它只在有人真的把日志打开看过之后才会被发现。

以后再设计任何可中断的流程，你会先想一件事：已经交付出去的那部分，存在哪里。

剩下没写的

这个仓库写完了 agent runtime 的主干，但有几块没碰：

工具调用（模型要求调工具、流式的参数片段、并发调度）、请求头与序列管理、系统提示词的归并、持久化到磁盘。

它们都不改变那三层循环的结构。工具调用会让 step() 返回 null，请求头管理是给 buildRequest 加约束，持久化是给 append 加一个后端。

都是出口条件的问题，不是结构的问题。

所以现在

你打开 agent.ts，第一反应应该不再是"从第一行开始读"。

找到了这个骨架，那 893 行的其余部分就都有了位置。它们不是 893 行逻辑，是三层循环的注脚。

我原以为工具越多，模型越强

一个 agent 有 20 个工具，听起来比有 5 个的强。所以看到 DSH 在 PTC 模式下只给模型一个工具的时候，我的第一反应是"这不是把能力砍了吗"。

砍掉的是直接调用，不是能力。所有工具仍然可用——只是必须从程序里调。

DSH 对模型的原文写得很直白：

run_code 是唯一你能直接调用的工具——指名任何其他工具的调用都会失败。所有工具都要从程序里面调用。

省下来的不是能力，是上下文

这一刀砍下去，最大的收益在提示词里。

原本每个工具都要写进模型上下文：名字、描述、参数 schema。20 个工具就是 20 份 schema，而且每次请求都要带。

PTC 模式下只剩一个 run_code 的 schema。其余工具以生成的 SDK 类型声明的形式出现——不是给模型"看"的说明文档，而是它写程序时依赖的类型信息。

工具显不暴露给模型，是一件成本决策，不是能力决策。

当然，代价是模型得会写代码。但对现在的模型来说，写一段 await tools.grep(...) 比读 20 份 JSON Schema 更接近它的训练分布。

三个和 Codex 不同的选择

同一件事——让模型写程序调工具——Codex 和 DSH 给出了不同的工程答案。对照着看最清楚。

选择一：程序一次跑完，不挂起

Codex 的 cell 可以挂起（Pending + WaitRequest），DSH 的程序从开始跑到结束。

这不是能力差异，是执行环境的差异推出来的：

  • Codex 的 code mode 跑在内嵌 V8 里，起一个执行环境几乎免费，所以可以随时挂起、恢复
  • DSH 的 PTC 跑在独立进程里（Node 或 CPython），启动成本高，所以一次跑完

独立进程换来的是真正的操作系统级隔离——Landlock、Seatbelt、bwrap 这些沙箱能作用在它身上。同一个进程里的 V8 隔离给不了这个。

要隔离强度，还是要不要挂起的能力，这是二选一。

选择二：状态不保留

DSH 的运行时契约里有一句话：每次运行都不会保留之前程序的状态。

code/step8-ptc.mjs 的最后一个场景把这件事跑出来了：

第一次运行里 const remembered = 42，第二次运行读不到。

这个设计是上一条的直接推论：既然每次都要起新进程，那就没有地方留状态。与其假装有个"会话变量"，不如明说没有——模型也就不会去依赖它。

要跨运行共享，得靠别的机制（文件、或者宿主自己的状态），而不是上一段程序留下的内存。

选择三：失败是字段，不是异常

run() 永远不会因为程序失败而 reject。失败是 PtcRunResult 上的一个字段。

边界上的几处谨慎

读 types.ts 的时候，有几处细节能看出这套东西被认真推敲过：

绑定参数必须是无损 JSON。 跨进程序列化会丢信息，所以运行时宁可拒绝这次运行，也不悄悄传过去一个被削过的值。

命名空间的全局名要语言可移植。 规则是 [A-Za-z_][A-Za-z0-9_]* 且不能是各语言的保留字——因为同一份绑定清单要能同时喂给 TypeScript 和 Python 后端，$tools 这种只有 JS 认的写法在设计上就被拒了。

console、__dsh_main__ 这类名字被预留。 它们在每个后端里都是运行时自己的槽位，不能被绑定占用。

这些规则单看都琐碎。合起来说明一件事：这个 seam 的设计目标是"换后端不改调用方"，所以任何后端特有的东西都不能泄漏到接口上。

下次再看到"给模型加工具"，除了问"这个工具给谁调"，再问一句：它需要跨调用保持状态吗？ 需要的话，你就得在处理"状态存在哪、活多久、谁能看到"上花掉不少设计预算。

每章配的代码都在 code/ 下，单独 node 就能跑，不依赖任何东西。
